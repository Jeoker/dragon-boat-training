# C2.4 报名与排座事件快照：本地前置切片

日期：2026-09-27。此切片**只改变本地 C1 报名／排座事务写入的 outbox 内容**；未部署 Worker、Apps Script 或 Pages，尚未向 Google `SignupsCurrent` 写入报名。独立 `c2test` 继续运行上次已验收的成员／赛季名单版本导出。

一次报名、换侧或取消可能同时改变发起人的状态、递补队员的状态及私有／已发布座位。十分钟后若只读取 Cloudflare 当前行，较晚操作会覆盖较早事件所代表的状态。现在每条新 `SIGNUPS_CHANGED` 事件在原报名事务中捕获 `snapshot_schema=2`、当时的 `practice_version` 和 `signup_version`，以及**当次实际变化的所有报名行**（含自动递补，按成员 ID 稳定排序）。每行包含稳定三元 ID、偏好、状态、原报名时间及序号、更新时间和请求 ID。原有发起人、递补 ID 及座位版本字段仍保留；无变化的同偏好更新仍不产生新事件。

若报名改变排座，同一事务再捕获 `seating_snapshot`：修改后的角色／版本／操作者状态、草稿发生变化时的完整左右船位，以及正式版发生变化时新建的不可变 revision、入座成员和当时的姓名快照。未改变的一侧明确为 `null`，避免把旧草稿误作为该事件的新目标。草稿和正式版同时变化、仅草稿变化及仅正式版变化均有回归；后续手动改动草稿不会修改已排队事件中的旧船位和正式 revision。这里保存的是 Cloudflare 源快照，还不是 Google Sheet 的目标行或已核验回执。

教练手动 `saveSeatPlanDraft`／`publishSeatPlan` 的 `SEATING_CHANGED` 事件也在各自事务内捕获 `snapshot_schema=1`、训练和报名版本，并使用同一个 `seatingExportSnapshot` 从**已持久写入的 SQLite 行**读取状态、必要的草稿船位及新正式 revision。手动草稿保存后正式发布、再改草稿的回归证明三条事件各自保留原状态；这避免了更早的手动排座事件成为后续报名导出的不可重建前置条件。报名事件与手动排座事件的 schema 编号分别为 2 和 1，须按 topic 解析，不能混用。

回归场景在 Google 尚未导出的情况下连续执行左侧报名、另一人左侧候补、首人换到右侧、取消及重新报名。五个 outbox 分别保留报名版本 1–5；第一条仍是首人的左侧状态，第三条同时包含首人右侧与候补递补后的左侧状态，第四条保留取消，第五条重新报名的排队序号从 1 变成 3，而数据库最新行已是重新报名后的状态。此测试验证了较晚修改不会重写早期事件的固定输入，不证明 Google 写回成功。

验证：`npm test` 192／192、`npm run cf:test` 103／103、`npm run cf:check` 通过。Wrangler 仍会打印本机日志目录 EPERM 与故障注入用例的 alarm 异常文本，测试进程退出码为 0；这些输出不等于远端负载或 Google 链路验收。

接下来的导出器必须拒绝没有完整快照的旧报名或手动排座事件，除非经过可核验的专门迁移；不得从当前行推测旧事件目标。写入前还须核验同绑定版本的成员与训练行、该事件前的报名 B/G 和连续 `signup_version`，并把捕获的座位源快照投影为 Google `SeatPlanState`、`SeatPlanCurrent` 和必要的 `SeatPlanRevisions` 目标。批次、每个目标及回执须固定保存；Google 多 Tab 不具备原子事务，**只有当次报名行和其引起的座位变化均核验后**才能确认原事件。`SignupsCurrent` 本身没有 `signup_version` 列；版本由 outbox 与 Cloudflare B／批次元数据跟踪，不应假称可在 Google 报名行直接读到该版本。真实部分写入及响应丢失、旧事件接续、训练／排座关联批次都留待后续切片。
