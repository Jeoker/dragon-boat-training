# C1.4 后代码健康审查

> 状态：2026-09-21 完成。本轮只修改本地源码、测试和说明并提交 Git，不部署 Apps Script、Cloudflare staging 或生产环境。生产仍由 Apps Script／Google Sheets 承担业务写入，Cloudflare 仍处于隔离迁移阶段。

## 审查范围

本轮复核 C1.4 排座契约、SQLite schema v5、排座服务、与 C1.3 报名事务的联动、影子导入、不可变回执、审计／outbox、公开与管理投影、专项测试及阶段说明。重点检查数据版本、导入重复执行、revision 连续性、姓名数据边界、角色与报名约束、请求重放和重复实现。

报名、换侧、取消及候补的产品规则没有改变：换侧保留原报名时间与队列身份；新侧有容量时可以保持或恢复为已确认，但不自动占用具体船位。若旧船位已因换侧释放并由其他人递补，原队员换回时仍按当前容量和原队列关系决定状态，Coach 再从待排座池安排实际行位。

## 已修复问题

1. **相同状态版本可静默覆盖元数据**：影子导入原先只比较角色和船位；当排座版本及正式 revision 都未变化时，`updated_by`、`updated_at` 仍可被另一个快照覆盖。现在完全相同的双版本要求状态元数据也一致，否则返回 `IMPORT_CONFLICT`。
2. **最新正式版没有按当前关系重新验证**：导入会验证私有草稿，但可能接受当前已候补成员担任 Coach／Steerer，或接受漏掉当前已确认报名的最新正式版。现在最新 revision 会按训练阶段重新验证成员、角色／报名冲突、船位资格和完整性。
3. **姓名快照允许无关成员**：原校验只要求参与者姓名齐全，额外成员也可进入不可变 revision。现在姓名集合必须精确等于 Coach、Steerer 和实际入座成员的去重集合，避免保存无关个人资料。
4. **大快照重复全表扫描**：每个场次都重新筛选全部草稿与 revision，复杂度随场次和行数相乘。现在导入开始时按赛季／场次建立索引，验证和写入共用分组结果；连续 revision 校验改为集合计数，不再按外部版本值逐个循环。
5. **报名投影和队列排序维护两份**：C1.3 与 C1.4 各自保存完全相同的帮助函数。现在统一到 `c1-support.ts`，防止后续一个路径修改而另一处漂移。
6. **发布幂等缺少直接回归**：专项测试原来覆盖草稿保存的重放和版本冲突，但没有直接证明发布接口的不可变结果。现在覆盖发布原请求重放、重放后刷新到最新工作区、同编号换参数冲突及另起请求携带旧版本被拒绝。

## 接口与事务结论

- 本轮没有增加或删除路由，也没有改变请求 DTO、成功 envelope、错误清单或 C1 服务版本。
- 保存草稿、发布正式版，以及报名变化触发的系统 revision，继续把业务状态、不可变回执、审计和单个对应 outbox 事件放在同一 SQLite 事务中。
- 影子导入继续不创建 Google outbox；省略记录不解释为删除。它只收紧冲突识别，不取得生产写入权。
- 公开投影仍只读取最新正式 revision，管理工作区才读取私有草稿。本报告完成时冻结投影仍使用当前成员姓名；C1.5 现已另建不可变历史快照，见[历史验收](C1-HISTORY-ACCEPTANCE.md)。
- C1.4 服务中仍存在按场次读取现有 revision 的数据库查询；它们用于和本地既有数据做逐项不可变比较，不是随输入行数反复扫描内存数组。当前迁移规模下无需为了减少查询而引入更复杂的缓存层。
